ユーザーテスト

User Testing

実際の利用者に試作品や製品を使ってもらい、その行動を観察して課題や気づきを見つける検証手法。

意味

ユーザーテストとは、実際に使う立場の人に試作品や製品を操作してもらい、その様子を観察して問題点や気づきを得る検証手法を指す。つくり手の想定と現実の使われ方のずれを、早い段階で確かめられる。

感想を尋ねるだけでなく、どこで迷い、どこで手が止まるかといった行動そのものを観る点が要になる。試作と組み合わせて反復することで、少ない手戻りで完成度を高めていける。

成り立ち

ユーザビリティ評価の実践から発展した手法で、少人数でも重大な問題の多くを発見できるとする議論などを通じて、反復的な検証の一環として定着した。

ユーザーテストと定性調査の違い

定性調査は、相手の語りから理由や背景を引き出す調査であり、答えは相手の言葉として返ってくる。ユーザーテストが見るのは、相手が実際にどう動いたかという行動そのものである。言えることとできることは一致しないため、拾える材料の種類が違う。

使い分けの目安は、知りたいことが理由か、つまずきかにある。なぜそれを選ぶのかを知りたいなら語りが要り、どこで手が止まるのかを知りたいなら操作を観るほうが早い。感想を尋ねる問いをテストの最中に挟むと、行動の観察がいつのまにか語りに置き換わってしまう。

ユーザーテストとデザインリサーチの違い

デザインリサーチは何をつくるべきかを探る側の活動で、ユーザーテストはつくったものが機能するかを確かめる側の活動である。前者は選択肢を広げるために行い、後者は絞った案の確からしさを測るために行う。工程のどこにいるかで呼び分けられる。

取り違えると、試作を前にしながら、本来なら手前で済ませておくべき問いを投げてしまう。この課題は本当に存在するのかという問いは、テストの場で扱うには遅い。テストで答えられるのはこの形で解けているかまでであり、解くべきかどうかは含まれない。

使いどころ

試作ができた段階で、代表的な利用者に使ってもらい観察する。見つかった課題を次の試作へ反映し、検証を繰り返す。

実務でのチェックポイント

  • テスト中に発した自分の言葉を振り返り、答えを誘導する説明をしていないか確かめる。操作前の説明が長いほど、素の行動は見えにくくなる。
  • 見つかった問題のうち、実際に次の試作へ反映されたものを数える。記録だけが増えているなら、検証が工程に接続していない。
  • 始める前に、何が分かればこの回は成功かを一文で決めているか確かめる。決めていないと、観察の焦点が散りやすい。
  • 参加者が途中で助けを求めた場面を挙げ、その場で手を貸したかを振り返る。助けた回数だけ、実際の使われ方は見えなくなっている。

よくある誤解

感想を集める場として運用されやすい。使いやすかったかと尋ねれば肯定的な答えが返りやすく、目の前の相手に配慮した回答が混ざる。観るべきなのは、どこで視線が止まり、どの操作をやり直したかという動きのほうで、言葉は動きを説明する補助として扱われる。

人数を集めれば精度が上がるという読み方もある。重大なつまずきは少人数でも繰り返し現れる一方、人数を増やしても、どの案が好まれるかという選好の比較は成立しにくい。数を増やして解決するのは代表性の問題であって、行動を観ることで得られる気づきの深さではない。

よくある質問

ユーザーテストは何人くらいに実施すればよいですか？

目的によって変わるが、つまずきを見つけるだけなら少人数で足りることが多い。同じ場所で複数人が詰まれば、それは個人差ではなく設計の問題として扱える。一方、どちらの案が好まれるかを比べたい場合は、少人数の観察では判断がつかず、別の方法が要る。

試作が粗くてもテストできますか？

できるし、粗いほうが向く場面もある。紙に描いた画面でも、順序の分かりにくさや言葉の通じなさは十分に現れる。完成度が高いと、相手は見た目の感想に寄りやすく、根本の構造への指摘が出にくくなる。何を確かめたいかに応じて、粗さを選ぶ対象として扱える。

社内の人間をテスト参加者にしてもよいですか？

代替にはなるが、見つかる問題の種類が限られる。仕組みや用語を知っている人は、初めて触れる人がつまずく場所を素通りしてしまう。手順の確認や進行の練習には使えるが、分かりにくさの発見という本来の目的には向かない。用途を分けて扱うことになる。
